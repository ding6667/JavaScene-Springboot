## AI 出题（Dify）报错定位
- 现象：前端申请 AI 出题，Dify 返回 `Output count is missing.`，出题失败（后端返回 0）。
- 定位：`docs/dify_workflow/出题智能体.yml` 迭代节点内的代码节点「对item提取」(id 1789021176741) 声明了 outputs `count/name/pointId`，但代码 `return {"result": {...}}`，键名与外层 output 声明不一致；Dify 按声明顺序校验，第一个缺失即 `count`。节点在迭代内且 error_handle_mode=terminated，故错误表现为迭代节点失败、整个工作流 failed。
- 附带发现：① 该节点 `count` 输出无人引用，迭代输出只取知识检索 result，单知识点题量信息丢失；② `chapter_name` 后端从未赋值（QuestionGenerateBizRequest/ExamQuestionGenerateServiceImpl 都缺），提示词「章节」恒为空；③ `QuestionAgentImpl.parseResponse` 只 log Dify 的 data.error，抛 AGENT_UNAVAILABLE，前端看不到真实原因；④ LLM structured_output 中 `total` 声明为 string，模型可能返回 number。
- 状态：仅诊断，未改任何代码/工作流，等用户指令。

## 备课 PPT 不生成文件 / pptxUrl 不回填（已修复）
- 现象：teach 备课 AI 生成后 pptxMd 有内容，但不产出 pptx 文件、`teach_prepare_record.pptx_url` 为空、`teach_ppt` 不落记录。
- 根因：`teach/.../util/MarkdownToPptxUtil.buildCommand` 把命令拼成 `marp2pptx convert <md> -o <pptx>`，而 marp2pptx 0.1.0 是单位置参数 CLI（`marp2pptx [-h] [-o OUTPUT] [--no-check] input`），无 convert 子命令。argparse 把 `convert` 当 input、真实 md 路径判为多余参数，退出码 2 → `convertContent` 返回 null → pptxUrl 为 null → 既不落 teach_ppt 也不回填 URL。实测旧命令 `EXIT=2`，新命令 `EXIT=0` 正常产出 pptx。
- 修复：`buildCommand` 改为 `List.of(marpCommand, mdFilePath, "-o", pptxPath)`；`convert()` 增加失败时打印命令 + 子进程输出尾部 20 行（原先只 debug 级、故障现场只有退出码无从定位）、以及退出码 0 但输出文件不存在的兜底判定；同步修正既有单测 `MarkdownToPptxUtilTest` 断言。
- 注意：本次仅改源码，按用户要求未编译未跑测试。历史已生成的备课记录 pptx_url 仍为空，需重新生成才会产出文件。

## PPT 下载接口支持「缺失即补生成」（前端无感）
- 需求：下载接口若没有 pptx_url，检查 pptx_md，有则重新生成文件、回填 pptx_url 并补 teach_ppt 记录；接口签名与返回结构不变。
- 实现：`PptServiceImpl.downloadPpt` 用 `isUsableFile` 判定（路径空 / 文件不存在都算缺失）→ `regeneratePptx` 按 recordId 加进程内互斥锁（`ConcurrentHashMap<Long,Object>`）+ 双重检查，避免并发重试生成多份；生成成功后用 entity+wrapper `update` 只回填 pptx_url（update_time 由 MetaObjectHandler 填充）。补生成失败时仍按原语义抛 `PREPARE_PPT_NOT_GENERATED` / `PPT_FILE_EXPIRED`，前端无感知。
- 复用：把主题注入从 `TeachPrepareAsyncServiceImpl` 抽成 `MarkdownToPptxUtil.injectStyle(md, css)` 静态方法（纯函数、不查库），备课生成与下载补生成共用，避免两套样式逻辑漂移；async 侧仍自行按 themeCode 查 CSS。
- 已知限制：`teach_prepare_record` 未存 theme_code，补生成时取系统默认模板（is_system=1/is_active=1/sort_order 最小）的 theme，若教师当初选了非默认模板，补生成的外观可能与首次不完全一致。要精确还原需给该表加 theme_code 列并在生成时落库。

## 列表/详情接口补 PPT 三态（hasPptMd + pptStatus）
- 根因：列表只返回 `hasPpt`（=pptx_url 非空），而生成链路是「先写 pptx_md，再异步转文件」，中间态在前端看来就是"没有 PPT"，无法分辨。
- 新增 `teach/util/PptAvailabilityUtil`：三态常量 `STATUS_NONE=0 / STATUS_MD_ONLY=1 / STATUS_READY=2`，`hasMd()` 与 SQL `TRIM(pptx_md)<>''` 等价，`isFileReady()` 用 `Files.exists` 判真实文件（路径非法/无权限/死链一律 false），`resolve(md,url)` 归并三态。列表、详情、下载三处共用同一口径（`PptServiceImpl.isUsableFile` 已改为委托它）。
- `PrepareRecordListResponse.Item` 增加 `hasPptMd`、`pptStatus`；**`hasPpt` 语义从「URL 非空」改为「文件真实存在」（=pptStatus==2）**，三者恒满足 hasPpt=(pptStatus==2)、hasPptMd=(pptStatus>=1)。
- `PrepareRecordDetailResponse` 增加 `hasPptMd`、`pptStatus`；`pptxUrl` 只在文件就绪时返回，否则置 null，不再下发会 404 的死链。
- 既有单测 `TeachPrepareRecordServiceImplTest.ownedRecord()` 改为把 pptx_url 指向 @TempDir 里真实创建的文件（否则 hasPpt 语义变更后用例必红），并补 hasPptMd/pptStatus 断言。未新增用例。
- 注意：备课每次都是 insert 新记录，因此不存在"重新生成时旧 pptx_url 残留指向旧文件"的问题；若将来引入同记录重试，转换失败时需显式把 pptx_url 置空（updateById 忽略 null）。

## 修复：备课 PPT 首页出现 CSS 全文 + 推理过程（marp2pptx 不支持 CSS）
- 现象：生成的 pptx 第 1 页开头是一整段 `<style>...</style>` CSS 文本，部分记录还夹着 `<think>...</think>` 的英文思考过程。
- 根因：**marp2pptx 不是 Marp CLI**，是纯 Python 的 Markdown 解析器（site-packages/marp2pptx/converter.py 的 `parse_marp` 自行剥 frontmatter、按 `\n---\n` 切页、逐行解析）。它不渲染 HTML、不解析 CSS，所以内联 `<style>` 块只是普通段落 → 整段 CSS 进第一页。
- 该工具的样式唯一入口：`config.py::load_config` 按顺序找 `<input>.yaml` → 同目录 `marp2pptx.yaml` → 内置 default.yaml（deep_merge）。可配置项见 default.yaml：colors(accent/accent_dark/text/gray/white/code_bg/table_header_bg)、fonts(main/mono)、font_ranges(按 slide class 的 [title_max, body_min, body_max])。已实测：同名 yaml 设 accent=#FF0000 后，默认 0078D4 完全消失。
- 修复（`MarkdownToPptxUtil`）：
  - 删除 `injectStyle`（CSS 内联注入），改为 `prepareMarkdown` = `stripReasoning` + `ensureFrontmatter`。
  - 新增 `buildThemeYaml(css)`：用正则解析 CSS 规则（先剥注释），把 h1.color→accent、h2.color→accent_dark、section.color→text、blockquote.color→gray、pre.background→code_bg、th.background→table_header_bg、section.font-family 首项→fonts.main。只认 #RGB/#RRGGBB，字号不映射（交给 auto-sizing，避免破坏排版）。
  - `convertContent(md, themeCss)` 新增两参重载：写临时 md 后，在**同目录同名** `<base>.yaml` 写主题配置（无主题写空注释占位，靠 `load_config` 遇同名即 break 屏蔽残留的 marp2pptx.yaml），finally 清理两者。单参 `convertContent(md)` 委托 `(md, null)`。
  - `stripReasoning`：删 `<think>|<thinking>` 配对块；未闭合的从标签删到文末；随后 `stripLeading()`（Dify 输出常见 `</think># 第8章` 直接相接）。
- 调用方：`TeachPrepareAsyncServiceImpl`（删 `injectTheme`，直接传 `getThemeStylesheet(themeCode)`）、`PptServiceImpl.writePptxAndRecord` 改为 `convertContent(md, resolveThemeCss(themeCode))`。
- 既有无用单测同步修正：`TeachPrepareAsyncServiceImplTest` 全部 stub/verify 改两参（`anyString(), nullable(String.class)`），两个断言 `<style>` 存在的用例改成"不注入 style + 校验 css 第二参数被传入"。
- 端到端验证（真实库数据 md=2114719260652380161 + java-default 主题 CSS）：首页只剩「第8章 类与对象 / Java程序设计基础 / 1 / 32」，无 style/think；主题色 1A56A0 生效、默认 0078D4 消失。空占位 yaml 回落默认外观且不报错。
- 已知边界：marp2pptx 只认颜色/字体/字号区间，CSS 里的 padding、border-radius、border-bottom 等无法映射，主题只能做到配色层面。历史已生成的脏 pptx 需重新生成（这两条 pptx_url 为 NULL，点下载会自动补生成）。

## PPT 生成选型调研（仅结论，未改代码）
- 根因认知：`marp2pptx` 是纯 Python 的 Markdown 解析器，不是 Marp。真正的 `@marp-team/marp-cli` 走 Chromium 渲染，CSS 完全生效；换工具是"最小改动、最大收益"的一档。
- 四条路线：① HTML 渲染导出（marp-cli/Slidev/reveal.js）保真高但默认整页图片不可编辑；② 直接画 OOXML（python-pptx/PptxGenJS/POI）可编辑但无排版引擎；③ **模板 + 占位符填充（pptx-automizer / python-pptx 改模板）观感最好且可编辑，长期推荐**；④ AI 一体化（Presenton、ppt-master）需独立部署、与现有 Dify 流程整合成本高。
- 决定观感的不是生成库而是模板 + 内容结构约束（每页要点数、字数上限、图表要求），建议在 Dify 侧加输出规范。
- AI PPT 产品共同架构（调研结论，可直接借鉴）：① LLM 只产出「中间表示 IR」——每页一个 card JSON（layout 枚举 + role + weight + 字符预算内要点），绝不让 LLM 给坐标；② 版式组件库 + 按内容特征打分匹配（对比→双栏、时序→时间轴、单指标→大数字）；③ 内容适配层 fit：字体度量算行宽 → 降字号 → 按 weight 截断要点 → 拆页；④ 渲染（OOXML 原生画 or HTML 转）→ 截图回看自检重排（PPTAgent 的 self-review / PPTEval 三维评估，中科院 EMNLP 2025）。
- 当前项目流程缺的正是 ②③④：markdown 只表达得了「标题+列表」，没有版式概念，也没有 fit，所以溢出/丑是必然。

## PPTAgent / DeepPresenter 接入可行性（调研，未动手）
- 许可 MIT，可商用；但形态是 **Python Agent 框架 + Docker 沙盒**，不是能嵌进 JVM 的库。
- 硬依赖：Linux/macOS/WSL2（**不支持 Windows**，本机 Windows 开发需 WSL2）、Python 3.12 + uv、Node、Docker（host + sandbox 两个镜像）、Playwright/Chromium、LibreOffice、poppler。
- 模型需求：research_agent / design_agent / long_context_model 必填，vision_model 强烈建议；官方推荐自家微调 DeepPresenter-9B。每页还要视觉审查多轮 → 单份课件几十次模型调用，耗时 5~15 分钟/6 页。
- 三个关键冲突：① 它自带 planner/research/design agent，会自己写内容，与现有 Dify 的 ppt_md 环节**职责重叠**，且没有"只排版"开关；② 生成太慢，**绝不能塞进下载接口的同步补生成链路**（HTTP 必超时），只能异步+轮询；③ 沙盒镜像需自行补中文字体，否则渲染成方块且视觉审查发现不了。
- 接入形态：CLI 子进程（最省事，同 marp2pptx 模式）/ Docker Compose sidecar（官方 host 只暴露 Web UI :7861，无稳定 REST，需自写 FastAPI 包一层）/ MCP（只适合 agent 客户端）。
- 更划算的中间路线：只抽它的 `deeppresenter/html2pptx` 子模块（HTML → 可编辑 pptx），不接整个 Agent，可避开 Docker/额外 LLM/9B 模型全部负担。
- 成本结构差异（关键判断依据）：Dify 是「按份 × 1 次长调用」，PPTAgent 是「按页 × 每页 N 次（设计 + 视觉审查 + 修订，其中视觉审查是图片输入）」→ 页数越多差距越大，20 页课件是最坏情况，量级在一个数量级以上而非"翻倍"。
- 真正的冲突不是钱而是**内容双写**：教案/重难点/作业/pptx_md 都由 Dify 产出，PPTAgent 自带 research/planner/design 会另起一套内容，两者不共享、风格会打架。要接必须先回答"谁是内容唯一来源"。
- 仓库现状（影响"fork 成本"判断）：主线已转向 **Skill 形态**（`skills/pptagent/SKILL.md` 驱动宿主 agent，research/planner/design 是 **prompt 驱动而非 Python 硬编码**；research 靠可选 MCP 工具 + Tavily/MinerU key）。另有 DeepPresenter CLI(`pptagent generate`) + Docker Compose host(:7861) 的独立形态并存。
- 因此"砍 research/planner"可能只需覆盖 SKILL.md + references/prompts.md，不必动 Python；但代价是要跑一个 host agent（Claude Code / Codex / OpenCode），等于后端再养一套 agent runtime，且无人值守要绕过 SKILL.md 里的 Review Gate。上游形态一年内变了三次（runtime → DeepPresenter v2 → Skill），fork 基线不稳定。
- 结论：不建议 fork 整仓库改流程；要"半自研"就选 ①只覆盖 prompt 文件 或 ③只摘 html2pptx converter。

## html2pptx 自拼链路（md → HTML → pptx）调研
- 注意：`icip-cas/PPTAgent` main 分支已无 `deeppresenter/html2pptx`（404，仓库重构过），只在 DeepPresenter fork 里。别把方案绑死单一仓库。
- 可直接用的现成实现：① `pip install html-to-pptx`（Design-Arena，playwright + python-pptx，CLI `html-to-pptx deck.html deck.pptx`，要求输入 1920×1080 画布、一页一个 `.slide` 容器，另有 extract_measurements/render_pptx 两段式 API）；② `microsoft/ResearchStudio` 的 `paper2poster/html2pptx`（python-pptx + lxml，带 vision audit 自检回路 + 18 条 GOTCHAS 文档，最值得读）；③ `arcsin1/oh-my-ppt`（Electron + pptxgenjs，**混合策略：背景整体截图当底图 + 文字/形状原生叠加**）。
- 两个实现家族：全原生（DOM walk + getComputedStyle + Range.getClientRects → 每块级元素一个文本框）vs 混合（背景截图 + 原生文字叠加，解决渐变/阴影/纹理无法转 OOXML 的问题）—— 教学课件选混合更划算。
- 核心难点是"文本排版冻结"：PowerPoint 重排规则与浏览器不同，只能三选一 —— 预断行（每行一个 run，编辑体验差）/ word_wrap=false（保真但改字会溢出）/ shrink-on-overflow。
- 关键 gotcha：字体名≠字体族（需 fontconfig alias）、比对图 DPI 统一 96、soffice 渲染≠PowerPoint 渲染、line-height 只在对的字体下生效、单个短文本设 word_wrap=false、表格/图表建议栅格化降级、变量字体要换静态字重。
- 第一段 marp-cli 出 HTML **不需要浏览器**（只有 --pdf/--pptx/--images 才起 puppeteer），所以只有第二段要吃 Chromium 成本。

## 最终技术选型结论（用户约束：长期不换技术、面向大学教师讲课、不要花哨外观、内容精美得体、外观易改）
- 重新定义选型对象：真正要锁定的是**中间表示 IR（SlideDeck DTO）+ 版式目录（语义版式枚举）+ 主题令牌（色板/字体/间距/字号阶）**；渲染器必须放在 `SlideRenderer` 接口后面保持可替换。这才是"以后换技术不用大改"的唯一保障；把 Markdown 当 IR 才是当前最大的锁定风险。
- 淘汰：① HTML→pptx（字体漂移、PowerPoint 重排不可控、需 Chromium/字体/LibreOffice 运维）；② Gamma 类自适应卡片（为"花哨"优化，与"得体"目标错位）；③ PPTAgent（内容双写 + 按页计费）；④ marp-cli --pptx-editable（实验性）。
- **选定：Apache POI XSLF 原生画 OOXML**。关键优势是"字体问题从根上不存在"——输出的是「文本 + 字体名 + 字号」，由 PowerPoint 在教师机器上渲染，无 Chromium 度量、无 LibreOffice 字体回退、无中文字体方块；且纯 Java 无子进程、100~300ms/20 页，可把"下载时补生成"退化为即时生成。
- 已确认 `common/pom.xml` 就有 `poi-ooxml 5.2.5`（目前仅 `FileFormatUtil` 用到），JDK 21 → 零新增依赖。
- 真实代价：fit（溢出适配）引擎要自己写。解法：把 Noto Sans SC（OFL）打包进 jar，用 `java.awt.Font` + `FontRenderContext` 在 headless 下做真实字体度量，不依赖服务器字体；三档降级 = 降字号 → 按 weight 截要点 → 拆页。
- 版式目录（12 个，先做 8）：封面 / 目录 / 章节过渡 / 单栏要点 / 双栏对比 / 图文 / 代码 / 表格 / 定义卡 / 案例引文 / 小结 / 结束页。
- 三个需现在拍板的细节：公式（LaTeX→PNG 或 OMML 手写 XML，先选 PNG）；图表（POI 原生 chart 或图片，先只做柱/折线/饼）；备注（XSLFNotes，教学场景价值高，必做）。
- 平滑迁移：新增 `md → IR` 降级解析器（只认标题/列表/代码块），历史 pptx_md 仍能出片（版式单一）；Dify 侧逐步把 pptx_md 换成每页一条的 JSON，Markdown 保留为兜底。
- 观感来源排序：内容约束（每页 3~5 要点、每点 ≤20 字）占七成，版式层级占三成，渲染技术几乎不贡献观感。

## Dify 备课工作流现状（影响 IR 改造量，重要）
- 文件 `docs/dify_workflow/备课智能体.yml` 是 Dify DSL 导出（改完需重新导入 Dify 才生效，改 yml 本身不改变线上应用）。
- 节点链：用户输入(start) → 素材重组与配置解析(code) → **PPT 起草(llm, json_object)** → 清洗PPT草稿(code) → **PPT 精修(llm, json_object, 评审专家角色)** → 其他材料生成(llm) → 汇总输出(code) → end。
- 现状输出已是 JSON：`PPT 起草` / `PPT 精修` 都是 `response_format: json_object`，但**结构只有 `{"pptx_md": "<整个 Marp Markdown 字符串>"}`** —— 结构化只到了"包一层"的程度，内容仍是纯 Markdown 文本。
- `汇总输出` 的 main() 返回 `{"output": {pptx_md, lesson_plan, key_points, homework, lab}}`；含 think/`<!--dify-deepseek-reasoning-->` 清洗、`_apply_ppt_cfg`（按 heading 正则删目录/小结页，依赖 "本节课内容"/"目录"/"小结"/"总结" 字面量）、`startswith("#","<!--","---")` 校验。pptx 开关为 1 而内容为空时抛 ValueError。
- **PPT 起草 prompt 里已定义 9 种页面类型 + 每页版式规范 + 数量约束 + 字数约束**：封面页 / 目录页 / 概念定义页 / 语法规则页 / 代码演示页 / 对比页 / 易错点页 / 随堂练习页 / 总结页。这套分类就是天然的 layout 枚举，比通用 12 版式更贴教学场景 → 后续版式目录应以它为准（并补 `mistake` / `quiz` 两个）。
- prompt 已禁止输出除 `<!-- _class: lead -->` 和 `<div class="columns">` 外的任何 HTML；`style_json` 仅影响语气，明令禁止写 CSS/颜色值。
- 因此 IR 改造量很小：只需把 `pptx_md: string` 换成 `slides: []`（每页带 layout 枚举），其余 4 个字段（lesson_plan/key_points/homework/lab）不动。灰度方案：Dify 同时输出 `slides` + `pptx_md`，后端优先 slides，缺失时走 md→IR 降级解析。
- 代码块在 JSON 里易被转义搞坏（引号/反斜杠），建议用 `lines: []`（字符串数组）而不是单个多行字符串。
- 不要在 IR 里出现坐标/颜色值，颜色只能是语义 token 名；否则换主题即废。

## 修复 teach 编译错误（10-28 傍晚）
- 报错 `TeachServiceImpl.java:326:68 QuestionItem无法转换为TeachHomeworkQuestion`。
- 根因：`loadSnapshotQuestions` 返回的是 `HomeworkDetailResponse.QuestionItem`（DTO），学生详情二次转换时把 DTO 传给了只收实体的 `renderConfigOrDefault(TeachHomeworkQuestion)`。
- 修法：`renderConfigOrDefault` 拆成三层重载 —— 实体版 / QuestionItem 版（两者都委托） / 核心版 `(JsonNode configured, Integer type, String content, String answerJson)`，兜底逻辑只留一份。
- 结论：教师详情与学生详情共用同一套 renderConfig 兜底口径；`TeachHomeworkQuestion` 的 `@TableName(autoResultMap = true)` + JacksonTypeHandler 已就位。
